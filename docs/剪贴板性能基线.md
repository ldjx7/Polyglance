# 剪贴板性能基线

## 测量范围

本轮新增 `clipboard-core` 的 `history_benchmark` 示例程序，使用文件数据库及完整公共 API，测量 500 条和 10000 条合成历史。程序使用独立临时目录，运行后清理；不打开应用历史，不访问系统剪贴板。可选导出只包含合成数据的备份，供 GUI 测试使用。

工作负载为 `clipboard-text-rich-metadata-v1`：8 个合成来源，每条约 750 字节文字，四分之一附带 HTML，每十条增加名称和标签，每二十条固定。核心测试期间关闭过期清理，条数容量等于测试规模；条目使用当前时间，导出的样本可按应用默认 30 天保留规则恢复。

每项操作先预热 5 次，再计时 40 次，记录中位数、P95、P99、均值、最小值和最大值。P95 是按样本排序后取向上取整的 95% 位置；40 次采样下的 P99 接近本轮最大值，只用于观察尾部波动。初始化另计，不加入查询耗时。新记录写入测试在容量已满时执行，包含非固定条目的淘汰。

此基线覆盖 Rust 数据库部分。AppKit、Slint、UniFFI、actor 调度、窗口绘制、图片解码、OCR 和系统剪贴板读取不在测量范围；CPU、能耗、GUI 内存和冷启动仍需实机测量。不同机器或不同负载的绝对数字不直接比较。

## 复现命令

在仓库根目录运行，使用 Release 构建。JSON 输出可保存在仓库外的结果目录：

```bash
cargo run --release -p clipboard-core --example history_benchmark --locked -- --items 500 --samples 40 > clipboard-core-500.json
cargo run --release -p clipboard-core --example history_benchmark --locked -- --items 10000 --samples 40 > clipboard-core-10000.json
```

生成可导入开发版的 10000 条合成备份：

```bash
cargo run --release -p clipboard-core --example history_benchmark --locked -- --items 10000 --samples 40 --export-fixture clipboard-fixture-10000 > clipboard-core-10000.json
```

输出目录必须不存在；程序拒绝替换已有目录。备份位于 `clipboard-fixture-10000/clipboard-10000.polyclipboard`，导出后会用默认保留期限恢复到独立临时引擎并核对完整条数。导出和复核不计入各项性能测量。

GUI 导入前先备份开发版原历史，再将最大条数设为 10000；否则应用会按当前限制清理多余的非固定记录。样本中 `benchmark.app.*` 是合成来源标识，没有对应应用图标。长期保存的样本仍受应用保留期限约束，过期后重新生成。

## 本地 Linux 初始结果

日期：2026-10-05 UTC。环境为 Linux x86_64 容器、Rust 1.95.0、Release 构建，报告可用并行度为 8。数据库位于容器临时文件系统，以下数字用于后续同环境复测。

核心源码基于 `35934f5`，性能示例为本轮新增。原始报告保留完整精度、样本数和时间戳：

- [500 条 JSON](benchmarks/clipboard/linux-500.json)
- [10000 条 JSON](benchmarks/clipboard/linux-10000.json)

单位为毫秒；下表为每项 40 次测量的 P95。

| 操作 | 500 条 | 10000 条 |
|---|---:|---:|
| 首页 100 条 | 1.807 | 6.034 |
| 末页 100 条 | 1.827 | 26.827 |
| 单一匹配搜索 | 2.578 | 30.716 |
| 中文多匹配搜索 | 1.090 | 6.279 |
| 无匹配搜索 | 1.526 | 32.591 |
| 类型、来源和标签组合筛选 | 1.223 | 7.447 |
| 刷新窗口需要的数据库调用合计 | 1.686 | 29.993 |
| 读取选中项载荷和注释 | 0.169 | 0.021 |
| 重复复制并更新原记录 | 0.982 | 6.730 |
| 新记录写入并淘汰旧记录 | 1.437 | 23.412 |

500 条初始化约 0.167 秒，10000 条约 23.917 秒；最终 SQLite 文件分别约 1.27 MiB 和 24.45 MiB。单项载荷读取差异主要落在亚毫秒区间，受调度与缓存影响，不据此推断更大数据库更快。

当前优先观察 10000 条时的稀疏/无匹配搜索、末页分页以及完整刷新。完整刷新依次调用列表、统计、固定键、来源和标签，包含当前实现的维护逻辑。下一步用同一平台和同一数据规模复测，并结合 GUI 延迟判断是否需要改动查询或缓存；本轮仅建立基线，没有修改生产查询策略。

## macOS 和 Windows CI

`Clipboard History CI` 增加同一套 Release 基线：macOS 在开发包构建后执行，Windows 在公共核心测试后执行；结果作为 `Clipboard-Performance-macOS` 和 `Clipboard-Performance-Windows` 附件保留 30 天。macOS 同时生成 500 条和 10000 条合成备份，随 `Clipboard-Acceptance-Materials` 上传。

CI 只要求命令和结果一致性检查成功，不以共享 runner 的固定耗时作为失败门槛。原生平台数据同样只表示公共核心性能。

### 后续定位顺序

1. macOS：用合成备份进入真实窗口，测量 10000 条时的搜索到渲染完成耗时，以及连续复制下的 CPU 和内存。现有核心数字尚不能说明实际窗口体验。
2. Windows：将满容量写入的 P95 约 297 毫秒列为接入前的性能关注项。当前采样来自共享 CI runner，先在目标机器复测，再分别记录事务提交、容量淘汰、`incremental_vacuum` 页回收的耗时，确认文件 I/O 与核心维护各自的影响。
3. 查询：在同平台复测稀疏查询、无匹配查询和深分页，确认是否需要减少重复维护或调整索引。任何修改继续验证清理规则、容量记账、事务回滚和删除后的空间回收。

本轮产出为测量工具、原始基线和验收准备；生产存储规则保持原实现。
